# Merge Sort: Guaranteed O(n log n)

Merge Sort is the gold standard of sorting algorithms when **guaranteed performance** and **stability** matter. Unlike Quick Sort which can degrade to O(n²), Merge Sort always runs in O(n log n) — every time, no exceptions.

The strategy: **split** the array in half recursively until individual elements, then **merge** sorted halves back together.

## The Merge Operation: The Heart of Merge Sort

```python
def merge(left, right):
    result = []
    i = j = 0

    # Compare front of each sorted half — take the smaller
    while i < len(left) and j < len(right):
        if left[i] <= right[j]:
            result.append(left[i])
            i += 1
        else:
            result.append(right[j])
            j += 1

    # Append remaining elements
    result.extend(left[i:])
    result.extend(right[j:])
    return result

def merge_sort(arr):
    if len(arr) <= 1:
        return arr
    mid = len(arr) // 2
    left = merge_sort(arr[:mid])
    right = merge_sort(arr[mid:])
    return merge(left, right)
```

## Why the Complexity Is Θ(n log n)

The recursion tree has **log n levels** (each split halves the problem). At each level, the total merge work is **O(n)** across all merges at that level:

```
Level 0: merge 2 halves of n/2    → n comparisons
Level 1: merge 4 halves of n/4    → n comparisons total
Level 2: merge 8 halves of n/8    → n comparisons total
...
Level log n: merge n halves of 1  → n comparisons total

Total: n × log n = Θ(n log n) — TIGHT BOUND, always
```

## The O(n) Space Cost

```python
# Every merge call creates a new list — this is the cost
def merge(left, right):
    result = []          # NEW list allocated — O(n) per level
    # ...

# At each level of recursion, temporary lists total O(n)
# There are log n levels... but lists are freed after each merge
# Peak memory usage: O(n) at any one time
```

This is why Merge Sort uses **O(n) auxiliary space** — fundamentally different from Quick Sort's in-place partitioning. For very large datasets (hundreds of GBs), this matters.

## In-Place Merge Sort

An in-place merge is possible but complex (O(n log²n) time). Python's `list.sort()` uses an **adaptive Merge Sort** (Timsort) that is partially in-place using galloping mode.

import time

def merge(left, right):
    result = []
    i = j = 0
    while i < len(left) and j < len(right):
        if left[i] <= right[j]:
            result.append(left[i])
            i += 1
        else:
            result.append(right[j])
            j += 1
    result.extend(left[i:])
    result.extend(right[j:])
    return result

def merge_sort(arr):
    if len(arr) <= 1:
        return arr
    mid = len(arr) // 2
    return merge(merge_sort(arr[:mid]), merge_sort(arr[mid:]))

# Bottom-up iterative merge sort (no recursion!)
def merge_sort_iterative(arr):
    n = len(arr)
    result = arr[:]
    width = 1
    while width < n:
        for i in range(0, n, 2 * width):
            left = result[i:i + width]
            right = result[i + width:i + 2 * width]
            merged = merge(left, right)
            result[i:i + len(merged)] = merged
        width *= 2
    return result

## Merge Sort vs Quick Sort Decision Matrix

| Factor | Merge Sort | Quick Sort |
|---|---|---|
| Worst case time | **O(n log n)** | O(n²) |
| Average time | O(n log n) | O(n log n) |
| Space | O(n) | O(log n) |
| Stable? | **Yes** | No |
| Cache performance | Poor (auxiliary arrays) | **Better** |
| Linked list sorting | **Optimal** | Needs random access |
| External sort (disk) | **Standard choice** | Impractical |

> **Pro Tip:** Use Merge Sort when you need: (1) **stability** (preserving equal element order), (2) **guaranteed** O(n log n) with no worst-case degradation, or (3) sorting a **linked list** (where Quick Sort's random access is slow).

> **Common Mistake:** Thinking Merge Sort is always "better" than Quick Sort. Merge Sort uses O(n) extra memory and has poor cache performance on arrays. For in-memory sorting of arrays where stability isn't needed, Quick Sort is typically faster.
