# URLs and Views

While Flask uses decorators (`@app.route`) to bind URLs directly to functions, Django separates the "Street Address" (URLs) from the "Building Blueprint" (Views) into distinct files.

Because a massive Django project may contain hundreds of URLs, keeping them organized in a central directory is crucial for maintainability.

## The `urls.py` File

Every Django app has a `urls.py` file. This acts as the master directory for your website. It uses a list called `urlpatterns` to match incoming web addresses.

```python
from django.urls import path
from . import views

# urls.py
urlpatterns = [
    # path(URL_string, View_function, Name_for_reverse_lookups)
    path('home/', views.home_page, name='home'),
    path('about/', views.about_page, name='about'),
]
```

## Path Converters (Dynamic URLs)

Just like we occasionally want users to visit `yoursite.com/users/alice`, Django supports dynamic variables in the URL path.

<interactive-code>
from django.urls import path
from . import views

urlpatterns = [
    # Captures an integer representing the article year
    path('articles/2003/', views.special_case_2003),
    
    # Captures any integer and passes it as 'year'
    path('articles/<int:year>/', views.year_archive),
    
    # Captures any string (excluding slashes) as 'slug'
    path('blog/<str:slug>/', views.blog_post),
]
</interactive-code>

When a user visits `/articles/2026/`, Django scans the `urlpatterns` top-to-bottom. It skips `articles/2003/`, successfully matches `<int:year>`, extracts the `2026` as an integer, and executes `views.year_archive(request, year=2026)`.

## The `views.py` File

So what actually *is* a view? A view is simply a Python function (or class) that takes a web request and returns a web response.

While the URL says "Oh, they want `/about/`", the view function is where you actually write the logic: reading the database, processing a form, and returning HTML.

<interactive-code>
from django.http import HttpResponse

# views.py
def home_page(request):
    # Every view takes an HttpRequest object as its FIRST parameter
    return HttpResponse("<h1>Welcome to the Home Page</h1>")

# This view expects the 'year' keyword argument captured by urls.py
def year_archive(request, year):
    # In a real app, we would query the database here
    return HttpResponse(f"Showing all articles from the year {year}.")
</interactive-code>

### The `HttpRequest` Object
Django automatically creates an `HttpRequest` object and passes it as the first argument to every view function. This object contains invaluable data, such as:
*   `request.method`: (e.g., 'GET' or 'POST')
*   `request.user`: The currently logged-in user
*   `request.POST`: A dictionary containing submitted form data

## Class-Based Views (CBVs)

As applications grow, you often find yourself writing the exact same code over and over: "Fetch a list of articles", "Fetch a list of products", "Fetch a list of users".

Django provides **Class-Based Views** (CBVs) that come entirely pre-written for common scenarios!

```python
from django.views.generic import ListView
from .models import Article

# Instead of writing a custom function to fetch a list of articles from 
# the database and send them to a template... just inherit ListView!
class ArticleListView(ListView):
    model = Article
    template_name = 'article_list.html'
    
    # Under the hood, this class writes a highly optimized SQL query
    # and passes the results to your HTML template automatically.
```

To use a Class-Based View in `urls.py`, you must call its `.as_view()` method:
```python
path('articles/', ArticleListView.as_view(), name='article-list'),
```

## Summary of the Request Cycle

The core request-response cycle in Django is incredibly strict:
1. User requests `/about/` in their browser.
2. Django looks inside `urls.py` to find a matching path.
3. `urls.py` routes the request to a specific function in `views.py`.
4. The function in `views.py` processes logic and returns an `HttpResponse` back to the user.
