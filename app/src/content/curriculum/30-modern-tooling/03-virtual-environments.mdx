# Virtual Environments (venv)

In the previous lesson, we saw that `pip` installs packages globally by default. If Project A needs Django 3.0 and Project B needs Django 4.0, a global install means you can only work on one project at a time. Updating Django for Project B will instantly break Project A.

This is solved using **Virtual Environments**.

A virtual environment is simply an isolated, self-contained directory tree that contains its own Python installation and its own `site-packages` folder. When a virtual environment is active, `pip` installs packages *only* into that environment, not globally.

## Creating a Virtual Environment

Python comes with the `venv` module built-in specifically for this purpose.

```bash
# Navigate to your project folder
$ cd my_project

# Create a virtual environment named "env" (or ".venv")
$ python -m venv env
```

This creates a new folder named `env` in your project directory. Inside `env`, you will find a copy of the Python executable and an empty `site-packages` directory.

## Activating the Environment

Before you can use the isolated environment, you must **activate** it. This temporarily changes your terminal's `PATH` variable so that when you type `python` or `pip`, it uses the executable inside your `env` folder, not the global one.

The activation command depends on your operating system:

```bash
# 🍏 macOS & 🐧 Linux
$ source env/bin/activate

# 🪟 Windows (Command Prompt)
$ env\Scripts\activate.bat

# 🪟 Windows (PowerShell)
$ env\Scripts\Activate.ps1
```

Once activated, your terminal prompt will usually change to indicate the active environment:
`(env) $ `

## Using the Virtual Environment

Now that it's active, any `pip install` command you run will place the package strictly inside `env/lib/pythonX.X/site-packages/`.

```bash
(env) $ pip install requests==2.28.1
(env) $ pip freeze > requirements.txt
```

Your global Python installation remains completely untouched! Project B can have its own `env` folder with completely different package versions.

## Deactivating

When you are done working on the project, you can exit the virtual environment by typing:

```bash
(env) $ deactivate
```
Your terminal prompt will return to normal, and `python` will once again point to your global installation.

## The Golden Rule of Git

Virtual environments contain thousands of files (the actual source code of your dependencies). **You should NEVER commit a virtual environment folder to version control (Git).**

Your `.gitignore` file should always contain:
```text
env/
.venv/
__pycache__/
```

Instead of sharing the `env` folder, you share the `requirements.txt` file. When another developer clones your repository, they will:
1. Create their own empty virtual environment.
2. Activate it.
3. Run `pip install -r requirements.txt` to perfectly recreate the environment on their machine.
