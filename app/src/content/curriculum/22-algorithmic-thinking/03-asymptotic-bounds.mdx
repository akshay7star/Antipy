# Asymptotic Bounds: The Full Picture

<BigOVisualizer />

Most engineers know **Big-O** as "worst case." That's close, but not mathematically accurate. Big-O is an *upper bound* — the algorithm won't do *worse* than this. But there are two other notations that complete the picture, and top-tier engineers understand all three.

## The Three Asymptotic Notations

| Notation | Name | Meaning | Analogy |
|---|---|---|---|
| **O(g(n))** | Big-O | Upper bound | "I will finish by 6 PM at the latest" |
| **Ω(g(n))** | Big-Omega | Lower bound | "I will start no earlier than 3 PM" |
| **Θ(g(n))** | Big-Theta | Tight bound | "I will finish between 5-6 PM, always" |

## Big-O: Upper Bound (Worst Case Ceiling)

f(n) = O(g(n)) means: for sufficiently large n, f(n) grows **no faster than** c × g(n) for some constant c.

```python
# Linear search: O(n) — worst case scans all n elements
def linear_search(arr, target):
    for i, val in enumerate(arr):
        if val == target:
            return i        # Best case: O(1) — found at index 0!
    return -1               # Worst case: O(n) — not found
```

> **Key insight**: O(n) doesn't mean "always n operations." It means the algorithm does **at most** n operations (times some constant). Linear search might terminate in 1 step — but we can't guarantee that.

## Big-Omega: Lower Bound (Best Case Floor)

f(n) = Ω(g(n)) means: f(n) grows **at least as fast as** g(n). This is the *best case guarantee*.

```python
# Any comparison-based sorting algorithm is Ω(n log n)
# You MUST look at at least n log n elements to sort n items.
# This is a mathematical proof, not an implementation detail.

# Ω(n log n) lower bound for sorting:
# To correctly sort n elements, we need at least log2(n!) comparisons
# By Stirling's approximation: log2(n!) ≈ n log n

# This means no matter how clever you are, you cannot beat O(n log n)
# for a general-purpose comparison sort.
```

## Big-Theta: Tight Bound (The Truth)

f(n) = Θ(g(n)) means the algorithm is **both** O(g(n)) and Ω(g(n)) — it grows exactly like g(n), tightly sandwiched from above and below.

```python
# Array traversal: Θ(n) — always visits EXACTLY n elements
def sum_all(arr):
    total = 0
    for x in arr:       # Always iterates exactly n times
        total += x
    return total        # No early exit — tight Θ(n)

# Binary search: Θ(log n) in the average case
# (But O(log n) worst case and Ω(1) best case — NOT tight!)
def binary_search(arr, target):
    lo, hi = 0, len(arr) - 1
    while lo <= hi:
        mid = (lo + hi) // 2
        if arr[mid] == target:
            return mid      # Ω(1) best case: found immediately
        elif arr[mid] < target:
            lo = mid + 1
        else:
            hi = mid - 1
    return -1
```

## Why This Matters In Practice

```python
# Hash table lookup:
# - Best case:  Ω(1) — no collision, direct bucket access
# - Worst case: O(n)  — every key hashes to same bucket (degenerate)
# - Average:    Θ(1)  — with a good hash function
# We say "O(1) average" but the WORST CASE is O(n)

# Quicksort:
# - Best case:  Ω(n log n) — perfect pivot splits
# - Worst case: O(n²)       — already sorted, pivot always smallest
# - Average:    Θ(n log n)
# We say "O(n log n) expected" but the GUARANTEE is only O(n²)

# Merge sort:
# - Best case:  Ω(n log n)
# - Worst case: O(n log n)
# - Always:     Θ(n log n) — this is a TIGHT bound
# Merge sort is the most predictable sorting algorithm
```

<interactive-code>
import time
import random

def measure(func, arr):
    start = time.perf_counter()
    func(arr[:])  # Work on copy
    return (time.perf_counter() - start) * 1000  # ms

# Bubble Sort — O(n²) worst, Ω(n) best (already sorted)
def bubble_sort(arr):
    n = len(arr)
    for i in range(n):
        swapped = False
        for j in range(n - i - 1):
            if arr[j] > arr[j+1]:
                arr[j], arr[j+1] = arr[j+1], arr[j]
                swapped = True
        if not swapped:
            break  # Already sorted — hits Ω(n) best case!
    return arr

n = 2000
sorted_arr   = list(range(n))       # Best case for bubble
reversed_arr = list(range(n, 0, -1)) # Worst case for bubble
random_arr   = random.sample(range(n), n)  # Average case

t_best  = measure(bubble_sort, sorted_arr)
t_worst = measure(bubble_sort, reversed_arr)
t_avg   = measure(bubble_sort, random_arr)

print(f"Bubble Sort on n={n}:")
print(f"  Best case  (Ω(n)  — sorted):   {t_best:.2f} ms")
print(f"  Average    (Θ(n²) — random):   {t_avg:.2f} ms")
print(f"  Worst case (O(n²) — reversed): {t_worst:.2f} ms")
print(f"\n  Worst/Best ratio: {t_worst/max(t_best,0.001):.1f}x slower")
print(f"  This demonstrates WHY bounds matter — huge real-world difference!")
</interactive-code>

## Amortized Analysis: Averaging Over Time

Sometimes an operation is occasionally expensive but cheap on average. **Amortized analysis** measures the *average cost per operation* over a sequence.

```python
# Python list.append() — amortized O(1)
# Most appends are O(1) — just fill a slot
# Occasional resize is O(n) — copy entire array
# But resize happens RARELY (array doubles each time)
# So: n appends cost O(n) total = O(1) amortized per append

lst = []
for i in range(1000000):
    lst.append(i)   # O(1) amortized — even though some are O(n)
```

> **Pro Tip:** In interviews, when you say "O(n)," be precise: say "O(n) worst case" or "O(1) average case." This shows you understand the nuance between upper bounds, tight bounds, and amortized complexity — a signal of senior-level thinking.

> **Common Mistake:** Treating O(n log n) as always better than O(n²). For very small n (like n=10), the constant factors matter more than the asymptotic class. Big-O describes *asymptotic* behavior — what happens as n → ∞.
